- 任务生产端（API 进程）将任务推入 Redis Stream

- 支持消费者组、消息确认（ACK）、未确认消息重试
- 支持优先级队列（`rag_flow_svr_task_broker:0/1/-1`）

## 三、设计巧思

### 3.1 任务分片策略

> 实现：[api/db/services/task_service.py:514](../../api/db/services/task_service.py) — `queue_tasks()`

**不同文件类型采用不同分片策略：**

| 文件类型 | 分片方式 | 分片大小 | 原因 |
|---------|---------|---------|------|
| PDF | 按页范围 | 默认 12 页/任务 | PDF 解析是 CPU 密集型，分片可并行处理 |
| 学术论文 | 按页范围 | 22 页/任务 | 学术论文单页信息密度较低 |
| Excel | 按行数 | 3000 行/任务 | 表格按行天然可分割 |
| 整文档解析 | 不分片 | 整文档 | 需要全局上下文（如 knowledge_graph） |
| 其他 | 不分片 | 整文件 | 文件通常较小 |

**巧思**：分片策略不是硬编码，而是根据 `parser_id` 和 `parser_config` 动态决定。`task_page_size` 可配置，不同场景灵活调整。

### 3.2 任务摘要（digest）与增量复用

> 摘要计算：[api/db/services/task_service.py:514](../../api/db/services/task_service.py) — `queue_tasks()`
> 复用逻辑：[api/db/services/task_service.py:688](../../api/db/services/task_service.py) — `reuse_prev_task_chunks()`

```python
# 对分块配置的所有字段排序后做 xxhash
hasher = xxhash.xxh64()
for field in sorted(chunking_config.keys()):
    hasher.update(str(chunking_config[field]).encode("utf-8"))
for field in ["doc_id", "from_page", "to_page"]:
    hasher.update(str(task.get(field, "")).encode("utf-8"))
task["digest"] = hasher.hexdigest()
```

**巧思**：
- 当用户修改解析配置后重新运行，只有配置变化了的分片需要重新解析
- 相同配置的历史 chunks 直接复用，避免重复的 LLM 调用和嵌入计算
- 排序字段再哈希，保证 digest 不受字段顺序影响

### 3.3 基于 Redis 标志的取消机制

> 取消设置：[api/db/services/task_service.py:760](../../api/db/services/task_service.py) — `cancel_all_task_of()`
> 取消检查：[api/db/services/task_service.py:783](../../api/db/services/task_service.py) — `has_canceled()`

```python
# 设置取消标志
REDIS_CONN.set(f"{task_id}-cancel", "x")

# 执行器定期检查
def has_canceled(task_id):
    return REDIS_CONN.exists(f"{task_id}-cancel")
```

**巧思**：不通过消息传递取消指令，而是用 Redis key 作为标志位。任务执行器在长时间操作（如 PDF 解析、embedding）的间隙检查这个标志。这比中断线程安全得多，也比消息队列方案简单。

### 3.4 交错启动避免连接风暴

> 实现：[rag/svr/task_executor.py:1661](../../rag/svr/task_executor.py) — `main()`

```python
worker_num = int(CONSUMER_NAME.rsplit("_", 1)[-1])
startup_delay = worker_num * 2.0 + random.uniform(0, 0.5)
await asyncio.sleep(startup_delay)
```

**巧思**：多个 task_executor worker 同时启动时，如果同时连接数据库和 Redis，会造成瞬时连接压力。通过基于 worker 编号的延迟启动，将初始化分散到不同时间点。

### 3.5 三小时超时保护

## 四、架构模式学习

### 4.1 生产者-消费者模式（Producer-Consumer）

```
API 进程（生产者）                  task_executor 进程（消费者）
        │                                      │
   queue_tasks()                        collect()
   queue_dataflow()                     do_handle_task()
        │                                      │
        └────── Redis Stream ──────────────────┘
```

- **解耦**：API 只负责创建任务，不等待执行结果。接口响应快，用户体验好
- **削峰**：大量文档同时触发解析时，Redis 队列缓冲，executor 按并发能力消费
- **可靠**：Redis Stream 的 ACK 机制保证任务至少被消费一次

### 4.2 两级并发控制

> 任务级信号量：[rag/svr/task_executor.py:139](../../rag/svr/task_executor.py) — `task_limiter`
> 图谱级信号量：[rag/svr/task_executor.py:143](../../rag/svr/task_executor.py) — `kg_limiter`

```
task_limiter = asyncio.Semaphore(MAX_CONCURRENT_TASKS)   # 全局任务并发上限
kg_limiter   = asyncio.Semaphore(2)                       # GraphRAG/RAPTOR 并发上限为 2
```

**巧思**：
- 全局信号量控制总并发，防止资源耗尽
- 知识图谱任务额外限制为 2（因为极其消耗 LLM token），避免挤占其他任务的模型配额
- 两级限流是经典的「粗粒度 + 细粒度」并发控制模式

### 4.3 策略模式的解析器工厂

```python
}
chunker = FACTORY.get(parser_id, naive)
chunks = chunker.chunk(name, file_bin, ...)
```

- 新增解析器只需实现 `chunk()` 方法并注册到 `FACTORY`
- 调用方通过字符串 ID 动态选择，不依赖具体类
- 符合**开闭原则**和**依赖倒置原则**

### 4.5 至少一次消费（At-Least-Once）

> 实现：[rag/svr/task_executor.py:211](../../rag/svr/task_executor.py) — `collect()`

```
collect():
  1. 先尝试从未确认（UNACKED）队列获取
  2. 再从正常队列获取
  3. 执行任务
  4. 成功后 ACK
```

如果 executor 在执行任务过程中崩溃，消息不会被 ACK，下次重启后会被重新消费。配合任务摘要（digest）和 chunk 复用机制，即使重复消费也不会产生重复数据。

### 4.6 回调驱动的进度上报

> 实现：[rag/svr/task_executor.py:161](../../rag/svr/task_executor.py) — `set_progress()`

```python
def set_progress(task_id, prog=None, msg="Processing..."):
    info = {"progress_msg": msg}
    if prog is not None:
        info["progress"] = prog
    TaskService.update_progress(task_id, info)
```

每个耗时步骤（解析、嵌入、入库）都接受 `progress_callback`，在关键节点回调更新进度。前端轮询文档状态即可获得实时解析进度。
