# 不同文件类型的切片策略 - 业务逻辑步骤

## 概述

当文档解析任务进入标准解析流程后，系统需要根据文件类型选择不同的切片策略。不同文件类型（DOCX、PDF、Excel、TXT、Markdown、HTML、EPUB、JSON、DOC 等）拥有不同的结构特征，因此需要定制化的解析和分块方案。

切片策略的选择分为两层路由：
1. **第一层路由**：根据文件扩展名判断文件类型大类，进入对应的解析分支
2. **第二层路由**：根据解析器配置（如 PDF 的布局识别器、Excel 的解析器选择）选择具体的解析方案

**核心原则**：每种文件类型的切片策略都遵循"解析结构 -> 文本规范化 -> 智能分块 -> 分词包装"的基本流程，但在每一步的执行细节上有所不同。

---

## 第一步：文件类型路由机制

### 1.1 文件类型大类判定

系统通过文件扩展名判断文件所属的大类：

| 大类 | 包含的扩展名 | 说明 |
|------|------------|------|
| PDF | `.pdf` | 便携式文档格式 |
| 文档 | `.docx`, `.doc`, `.txt`, `.md`, `.markdown`, `.mdx`, `.html`, `.htm`, `.epub`, `.json`, `.jsonl`, `.ldjson`, `.csv`, `.xlsx`, `.xls`, `.py`, `.js`, `.java`, `.c`, `.cpp`, `.h`, `.php`, `.go`, `.ts`, `.sh`, `.cs`, `.kt`, `.sql` 等 | 各类文档和代码文件 |
| 音频 | `.wav`, `.flac`, `.mp3`, `.aac`, `.ogg`, `.opus` 等 | 音频文件 |
| 视觉 | `.jpg`, `.jpeg`, `.png`, `.gif`, `.svg`, `.webp`, `.mp4`, `.avi`, `.mkv` 等 | 图片和视频文件 |
| 其他 | 其余扩展名 | 不支持的类型 |

### 1.2 解析器类型路由

在大类判定后，根据知识库配置的 `parser_id`（即 chunk_method）选择对应的解析器模块：

| 解析器 ID | 适用场景 | 说明 |
|-----------|---------|------|
| `naive` / `general` | 通用文档 | 默认解析器，支持最多文件格式 |
| `paper` | 学术论文 | 提取标题、作者、摘要等结构 |
| `book` | 书籍文档 | 层次化结构解析 |
| `laws` | 法律文档 | 条款结构识别 |
| `manual` | 使用手册 | 问答格式 |
| `qa` | 问答对 | 问答对提取 |
| `table` | 表格数据 | 每行作为独立记录 |
| `resume` | 简历 | 结构化信息提取 |
| `presentation` | 演示文稿 | PPT/PPTX 解析 |
| `picture` | 图片 | OCR + 视觉模型描述 |
| `one` | 整文档 | 整个文档作为单个 chunk |
| `audio` | 音频 | 语音转文字 |
| `email` | 邮件 | EML/MSG 解析 |
| `tag` | 标签 | 内容 + 标签分类 |

### 1.3 特殊文件类型的自动路由

无论知识库配置了什么解析器，以下文件类型会自动路由到专用解析器：
- **图片类型**（VISUAL） -> 强制使用 `picture` 解析器
- **音频类型**（AURAL） -> 强制使用 `audio` 解析器
- **演示文稿**（`.ppt`, `.pptx`, `.pages`） -> 强制使用 `presentation` 解析器
- **邮件文件**（`.msg`, `.eml`） -> 强制使用 `email` 解析器
- 其他文件 -> 使用知识库配置的默认解析器

**可能失败**：文件扩展名不在支持列表中 -> 返回"文件类型不支持"错误

## 第二步：DOCX 文档切片策略

适用于扩展名：`.docx`

### 2.1 可选的超链接分析

**触发条件**：解析配置中 `analyze_hyperlink = true` 且为根调用（非递归）

1. 从 DOCX 文件的 XML 关系中提取所有超链接 URL
2. 对每个超链接 URL：
   - 下载链接指向的网页内容
   - 尝试按原始 URL 格式解析（如链接指向 PDF 则按 PDF 解析）
   - 若原始格式解析失败，则按 HTML 格式解析
3. 将超链接内容的解析结果合并到主文档结果中

**可能失败**：网页不可达或内容为空 -> 跳过该链接，继续处理其他链接

### 2.2 修复 python-docx 已知问题

1. 替换 python-docx 库中的 XML 关系列表加载方法
2. 过滤掉无效的关系引用（如 `../NULL`、`NULL`、`#` 开头的内部引用）
3. 避免解析时出现 "There is no item named 'word/NULL' in the archive" 错误

### 2.3 解析 DOCX 文档结构

1. **遍历文档所有块**（段落和表格，保持文档顺序）
2. **处理段落**：
   - 提取段落文本内容，清理全角空格等
   - 识别段落样式（普通段落、标题 Heading 1-7、说明文字 Caption 等）
   - 提取段落中嵌入的图片
   - 通过 `lastRenderedPageBreak` 和 `w:br` 标签追踪页码变化
3. **处理表格**：
   - 将表格转换为 HTML 格式
   - 检测合并单元格并生成 `colspan` 属性
   - 查找表格之前最近的标题层级，生成如"文档名 > 一级标题 > 二级标题"的层级路径
   - 将层级路径作为表格的 `<caption>` 元素
4. **处理图片**：
   - 将 Caption 样式的段落与最近的图片关联
   - 未关联的图片作为独立的图片元素输出
5. **输出统一格式**：每个元素为三元组 `(text, image, table)`

### 2.4 文本规范化（RTL 语言支持）

1. 对所有解析出的文本段落进行阿拉伯语等 RTL（从右到左）语言的字符规范化
2. 将阿拉伯语的呈现形式字符转换为标准形式
3. 支持元组格式、列表格式和纯字符串格式的规范化

### 2.5 智能分块（DOCX 专用）

1. 使用 DOCX 专用的分块算法（naive_merge_docx），传入参数：
   - `chunk_token_num`：块的最大 token 数（默认 128）
   - `delimiter`：分句分隔符（默认 `\n!?。；！？`）
   - `table_context_size`：表格前后保留的上下文文本行数
   - `image_context_size`：图片前后保留的上下文文本行数
2. 分块算法同时输出：
   - `chunks`：分块后的文本列表（每个元素为字典，包含文本内容等）
   - `images`：包含图片的 chunk 索引列表

### 2.6 视觉增强（可选）

1. 对包含图片的 chunk，使用视觉模型（IMAGE2TEXT）理解图片内容
2. 生成图片的文本描述
3. 将图片描述追加到对应 chunk 的文本内容中

**可能失败**：视觉模型未配置或不可用 -> 跳过视觉增强，保留原始文本

### 2.7 分词包装与结果合并

1. 对所有 chunk 进行分词处理（支持带图片的 chunk）
2. 处理子元素分隔符（children_delimiter），支持自定义分隔符
3. 合并三部分结果：
   - 主文档分块结果
   - 嵌入文件的解析结果（如果有嵌入文件）
   - 超链接内容的解析结果（如果有超链接分析）

## 第三步：PDF 文档切片策略

适用于扩展名：`.pdf`

### 3.1 解析器配置初始化

1. 从解析配置中获取 `layout_recognize`（布局识别器）参数
2. 规范化布局识别器名称（处理大小写、空格等）
3. 提取关联的模型名称（如 MinerU 模型、PaddleOCR 模型）

### 3.2 可选的超链接提取

**触发条件**：解析配置中 `analyze_hyperlink = true` 且为根调用

1. 从 PDF 二进制数据中提取所有超链接 URL
2. 超链接的递归解析在分块完成后统一执行（参见 3.9）

### 3.3 选择 PDF 解析器

系统支持以下六种 PDF 解析器，通过 `layout_recognize` 配置选择：

| 解析器 | 配置值 | 说明 | 特点 |
|--------|-------|------|------|
| DeepDOC | `DeepDOC`（默认） | RAGFlow 自研解析器 | OCR + 布局分析 + 表格识别 |
| MinerU | `MinerU` | 深度学习 OCR 解析器 | 适合扫描件、图片型 PDF |
| Docling | `Docling` | AI 文档理解工具 | 智能识别文档结构 |
| TCADP Parser | `TCADP Parser` | 腾讯云文档解析服务 | 云端解析，支持多种输出格式 |
| PaddleOCR | `PaddleOCR` | 百度开源 OCR | 中文识别效果好 |
| Plain Text | `PlainText` | 纯文本提取 | 速度快，无布局分析 |

**特殊说明**：当 `layout_recognize` 配置为非 Plain Text 的其他值时，系统会尝试使用视觉模型（IMAGE2TEXT）解析 PDF，需要提供 `tenant_id`。

**可能失败**：
- 指定的解析器未安装或未配置 -> 回退到 Plain Text 解析器
- 使用视觉模式但未提供 tenant_id -> 抛出参数错误

### 3.4 调用解析器执行解析

1. 传入参数：文件名、二进制数据、页码范围（from_page, to_page）、语言、回调函数
2. 解析器输出：
   - `sections`：文本段落列表，每个元素为 `(text, tag)` 元组
   - `tables`：表格列表，每个表格包含 HTML 格式数据
   - `pdf_parser`：解析器实例（用于后续分词位置标注）
3. 对解析结果进行 RTL 文本规范化

**可能失败**：解析结果为空（sections 和 tables 都为 None） -> 返回空列表

### 3.5 表格和图片上下文增强

**触发条件**：`table_context_size > 0` 或 `image_context_size > 0`

1. 根据配置的上下文大小，在表格和图片前后保留相应数量的文本行
2. 将上下文文本附加到表格/图片的描述中
3. 提升检索时的上下文关联性

### 3.6 内置分块解析器的特殊处理

以下解析器在解析阶段已完成分块，不需要后续的 naive_merge 分块：
- TCADP Parser
- Docling
- MinerU
- PaddleOCR

**处理方式**：将这些解析器的 `chunk_token_num` 设为 0，禁用后续的通用分块逻辑。

### 3.7 表格分词

1. 将解析出的表格列表进行分词处理
2. 表格以 HTML 格式存储，支持全文检索

### 3.8 通用分块逻辑

对于 DeepDOC 和 Plain Text 解析器，解析结果需要经过通用分块：
1. 使用 `naive_merge` 算法，按 `chunk_token_num` 和 `delimiter` 参数分块
2. 支持 `overlapped_percent`（重叠百分比），在相邻块之间保留重叠内容
3. 使用 `tokenize_chunks` 进行分词包装

### 3.9 超链接递归解析

**触发条件**：`analyze_hyperlink = true` 且存在提取的超链接

1. 对每个超链接 URL：
   - 下载网页内容
   - 尝试按原始 URL 格式解析
   - 解析失败则按 HTML 格式解析
2. 将超链接解析结果合并到主文档结果中

## 第四步：Excel/CSV 文档切片策略

适用于扩展名：`.csv`, `.xlsx`, `.xls`

Excel/CSV 的切片策略有两条路径：

### 4.1 TCADP Parser 路径（云端解析）

**触发条件**：解析配置中 `layout_recognize = "TCADP Parser"`

1. **初始化解析器**：
   - 传入 `table_result_type`（表格输出格式）和 `markdown_image_response_type`（图片响应类型）
   - 检查 TCADP 服务是否可用

2. **确定文件类型**：
   - `.xlsx` 或 `.xls` -> XLSX 类型
   - `.csv` -> CSV 类型

3. **调用 TCADP 云端解析**：
   - 输出格式支持 Markdown、HTML、JSON 等
   - 解析结果包含文本段落和表格

4. **禁用后续分块**：设置 `chunk_token_num = 0`，因为云端解析已完成分块

**可能失败**：TCADP 服务未配置或不可用 -> 返回空结果，提示检查腾讯云 API 配置

### 4.2 DeepDOC 默认路径（本地解析）

**触发条件**：`layout_recognize` 不为 "TCADP Parser"（默认路径）

**分支 A：HTML 格式输出**

**触发条件**：解析配置中 `html4excel = true`

1. 使用 ExcelParser 将表格按每 12 行一组输出为 HTML 格式
2. 禁用后续分块（`chunk_token_num = 0`）

**分支 B：纯文本格式输出（默认）**

1. 使用 ExcelParser 逐行提取表格数据
2. 每行作为一个独立的文本段落
3. 后续通过通用分块逻辑处理

### 4.3 RTL 文本规范化

对所有提取的文本段落进行阿拉伯语等 RTL 语言的字符规范化。

## 第五步：TXT/代码文件切片策略

适用于扩展名：`.txt`, `.py`, `.js`, `.java`, `.c`, `.cpp`, `.h`, `.php`, `.go`, `.ts`, `.sh`, `.cs`, `.kt`, `.sql`

### 5.1 行级拆分

1. 使用纯文本解析器（TxtParser）处理文件
2. 根据配置的分隔符（默认 `\n!?;。；！？`）将文本按行拆分
3. 按 `chunk_token_num`（默认 128）的 token 限制合并行为块
4. 空行被过滤

### 5.2 RTL 文本规范化

对拆分后的文本段落进行 RTL 语言规范化。

### 5.3 通用分块

1. 使用 `naive_merge` 算法，将段落合并为不超过 token 限制的块
2. 支持 `overlapped_percent`（重叠百分比）
3. 使用 `tokenize_chunks` 进行分词包装

---

## 第六步：Markdown 文档切片策略

适用于扩展名：`.md`, `.markdown`, `.mdx`

### 6.1 解析 Markdown 结构

1. **读取文件内容**：自动检测文件编码
2. **提取表格和剩余文本**：分离 Markdown 表格（使用 `|` 语法）和普通段落
3. **提取图片引用**：
   - 支持 Markdown 格式 `![alt](url)`
   - 支持 HTML 格式 `<img src="url">`
   - 记录每个图片 URL 所在的行号
4. **按分隔符分段**：使用 MarkdownElementExtractor，按标题层级和分隔符将文档拆分为段落
5. **为每个段落加载关联图片**：
   - 根据图片行号与段落行号范围的匹配关系
   - 支持从 HTTP/HTTPS URL 下载图片或从本地路径加载
   - 多个图片合并为一张
6. **转换表格为 HTML**：使用 Markdown 表格扩展

### 6.2 可选的视觉模型图片增强

**触发条件**：租户配置了 IMAGE2TEXT 类型的视觉模型

1. 检测租户是否配置了视觉模型
2. 对每个包含图片的段落：
   - 合并段落内的多张图片
   - 使用视觉模型生成图片的文本描述
   - 将图片描述追加到段落文本末尾
3. 视觉模型不可用时跳过此步骤

### 6.3 可选的超链接提取

**触发条件**：解析配置中 `hyperlink_urls = true` 且为根调用

1. 对每个段落的 Markdown 文本转换为 HTML
2. 从 HTML 中提取所有 `<a>` 标签的 `href` 属性
3. 收集所有 URL 用于后续递归解析

### 6.4 表格分词

1. 将 Markdown 表格转换为 HTML 格式
2. 使用 `tokenize_table` 进行分词处理

### 6.5 Markdown 专用分块逻辑

Markdown 使用不同于 naive_merge 的专用分块逻辑：

1. **逐段落遍历**：按顺序遍历所有段落
2. **Token 计数**：计算每个段落的 token 数
3. **块合并**：
   - 当当前块的 token 数加上新段落超出 `chunk_token_num` 限制时：
     - 保存当前块
     - 计算重叠部分（如果 `overlapped_percent > 0`）
     - 从重叠部分开始新块
   - 否则将新段落追加到当前块
4. **图片关联**：每个块保留其关联的图片
5. **分词包装**：
   - 如果块中包含图片 -> 使用 `tokenize_chunks_with_images`
   - 如果无图片 -> 使用 `tokenize_chunks`

### 6.6 超链接递归解析

与 PDF 策略相同，对提取的超链接进行递归解析。

---

## 第七步：HTML 文档切片策略

适用于扩展名：`.htm`, `.html`

### 7.1 标签清理与结构提取

1. 使用 HTML 解析器（HtmlParser）处理文件
2. 清理 HTML 标签，保留文本内容
3. 保留文档的基本结构层次

### 7.2 分块处理

1. 按 `chunk_token_num`（默认 128）的 token 限制进行分块
2. 过滤空内容段落
3. RTL 文本规范化

### 7.3 通用分块

使用 `naive_merge` 算法分块，支持 `overlapped_percent` 和自定义分隔符。

---

## 第八步：EPUB 电子书切片策略

适用于扩展名：`.epub`

### 8.1 章节识别与内容提取

1. 使用 EPUB 解析器（EpubParser）处理文件
2. 识别电子书的章节结构
3. 提取每个章节的文本内容
4. 保留元数据信息（书名、作者等）

### 8.2 分块处理

1. 按 `chunk_token_num`（默认 128）的 token 限制进行分块
2. 过滤空内容段落
3. RTL 文本规范化

### 8.3 通用分块

使用 `naive_merge` 算法分块，支持 `overlapped_percent` 和自定义分隔符。

---

## 第九步：JSON/JSONL 文档切片策略

适用于扩展名：`.json`, `.jsonl`, `.ldjson`

### 9.1 对象级拆分

1. 使用 JSON 解析器（JsonParser）处理文件
2. 根据文件格式选择解析方式：
   - `.json`：解析为 JSON 数组，每个元素作为一个独立段落
   - `.jsonl` / `.ldjson`：逐行解析，每行一个 JSON 对象
3. 每个对象序列化为文本字符串

### 9.2 分块处理

1. 按 `chunk_token_num`（默认 128）的 token 限制进行分块
2. 如果单个 JSON 对象超过 token 限制，会被截断
3. 过滤空内容段落
4. RTL 文本规范化

### 9.3 通用分块

使用 `naive_merge` 算法分块，支持 `overlapped_percent` 和自定义分隔符。

---

## 第十步：DOC 旧版 Word 文档切片策略

适用于扩展名：`.doc`

### 10.1 使用 Tika 解析器

1. 检查 Apache Tika 是否已安装
2. 将文件二进制数据传入 Tika 解析器
3. Tika 从 DOC 文件中提取纯文本内容
4. 按换行符拆分为段落

**可能失败**：
- Tika 未安装 -> 返回空结果，提示 "tika not available"
- Tika 解析返回空内容 -> 返回空结果

### 10.2 分块处理

1. 过滤空内容段落
2. RTL 文本规范化
3. 使用 `naive_merge` 算法分块

## 通用配置参数说明

以下是所有文件类型切片策略中使用的通用配置参数：

| 参数名 | 类型 | 默认值 | 说明 |
|--------|------|--------|------|
| `chunk_token_num` | int | 128（naive）/ 512（book/laws） | 每个分块的最大 token 数。设为 0 则禁用后续分块 |

## 通用后处理流程

所有文件类型在完成各自的切片策略后，都经过以下统一的后处理步骤：

### 步骤 A：RTL 文本规范化
对所有解析出的文本进行阿拉伯语等从右到左（RTL）语言的字符呈现形式规范化。

### 步骤 B：通用分块（naive_merge）
对于需要通用分块的文件类型：
1. 使用分隔符将连续文本切分为句子片段
2. 将句子片段按顺序合并，直到达到 `chunk_token_num` 限制
3. 超出限制时开始新块，根据 `overlapped_percent` 保留重叠内容
4. 支持 `tokenize_chunks`（无图片）和 `tokenize_chunks_with_images`（有图片）两种分词方式

### 步骤 C：超链接递归解析
对于启用了超链接分析的文档：
1. 收集所有超链接 URL
2. 逐个下载并解析链接内容
3. 解析失败的链接按 HTML 格式重试
4. 合并超链接解析结果到主文档结果

### 步骤 D：嵌入文件处理
对于包含嵌入文件的文档（如 DOCX 中嵌入的其他文件）：
1. 从二进制数据中提取嵌入文件
2. 递归调用对应的切片策略解析嵌入文件
3. 合并嵌入文件的解析结果到主文档结果

### 步骤 E：结果合并与返回
1. 合并主文档分块结果、嵌入文件结果、超链接结果
2. 返回最终的 chunk 列表

**可能失败**：嵌入文件解析失败 -> 记录错误日志，跳过该嵌入文件继续处理

## 注意事项

1. **递归控制**：超链接分析和嵌入文件解析通过 `is_root` 参数控制，只在根调用时执行，避免无限递归
2. **解析器降级**：当指定的解析器（如 MinerU、Docling、TCADP）不可用时，系统会回退到 Plain Text 解析器或返回空结果
3. **编码检测**：对于 TXT、Markdown 等文本文件，系统自动检测文件编码，支持 UTF-8、GBK、GB2312 等多种编码
4. **分块粒度**：`chunk_token_num = 0` 表示禁用后续分块，保留解析器原始输出的粒度
5. **视觉增强依赖**：图片视觉增强功能需要租户配置 IMAGE2TEXT 类型的视觉模型，未配置时自动跳过
6. **PDF 分片并行**：PDF 文档在任务创建阶段会按页码范围拆分为多个任务并行解析，每个任务独立执行上述切片策略
