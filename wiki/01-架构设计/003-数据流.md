## 目的

这篇文档不再从“模块分层”看系统，而是从“事情是怎么流动的”来看。

对于 RAGFlow，最值得掌握的不是所有类名，而是下面四条主链路：

1. 文档处理流
2. 检索生成流
3. Agent 执行流
4. 对话与事件流

把这四条链路串起来，基本就能理解项目的大部分运行方式。

## 1. 文档处理流

文档处理流关注的是：原始文件如何变成可检索的数据。

```mermaid
flowchart TB
    U["用户上传文件"]
    U --> F["文件接收与存储<br/>api/apps + file service"]
    F --> T["创建解析任务<br/>document service / task service"]
    T --> P["选择解析器<br/>rag/app + deepdoc/parser"]
    P --> X["提取文本与结构"]
    X --> C["分块与规范化<br/>rag/flow/chunker"]
    C --> E["向量化 / Embedding"]
    E --> I["索引与入库<br/>ES / Infinity + MySQL"]
    I --> D["文档可用于检索"]
```

关键目录：

- [api/apps/](../../api/apps/)
- [api/db/services/document_service.py](../../api/db/services/document_service.py)
- [api/db/services/task_service.py](../../api/db/services/task_service.py)
- [rag/app/](../../rag/app/)
- [deepdoc/parser/](../../deepdoc/parser/)
- [rag/flow/chunker/](../../rag/flow/chunker/)

这条链路最常见的问题点：

- 文件类型识别错误
- 解析器选择不正确
- PDF / OCR 质量问题
- 分块策略不合理
- 向量化或入库失败

## 2. 检索生成流

检索生成流关注的是：用户问题如何变成最终答案。

```mermaid
flowchart TB
    Q["用户提问"]
    Q --> PRE["请求进入对话入口"]
    PRE --> RET["召回候选内容<br/>向量检索 / 关键词检索 / 混合检索"]
    RET --> RERANK["重排与筛选"]
    RERANK --> CTX["组装上下文与 Prompt"]
    CTX --> LLM["调用 LLM 生成回答"]
    LLM --> OUT["流式输出 / 保存结果"]
```

关键目录：

- [api/db/services/dialog_service.py](../../api/db/services/dialog_service.py)
- [api/db/services/dialog_service.py](../../api/db/services/dialog_service.py)
- [rag/nlp/search.py](../../rag/nlp/search.py)
- [rag/llm/](../../rag/llm/)

这条链路最常见的问题点：

- 没检索到正确片段
- 检索到了但排序不对
- Prompt 组装不稳定
- LLM 输出质量波动

## 3. Agent 执行流

Agent 执行流关注的是：Canvas/DSL 如何变成真正执行的组件图。

```mermaid
flowchart TB
    DSL["Canvas DSL / Workflow"]
    DSL --> LOAD["加载图与组件定义<br/>agent/canvas.py"]
    LOAD --> INIT["实例化组件参数与对象"]
    INIT --> VAR["解析变量引用"]
    VAR --> RUN["调度执行节点"]
    RUN --> INVOKE["调用具体组件逻辑"]
    INVOKE --> CTRL["分支 / 循环 / 迭代控制"]
    CTRL --> EVENT["推送执行事件"]
    EVENT --> DONE["输出最终结果"]
```

关键目录：

- [agent/canvas.py](../../agent/canvas.py)
- [agent/component/](../../agent/component/)

这条链路最常见的问题点：

- DSL 结构与当前组件 schema 不一致
- 变量解析失败
- 组件输出格式不符合下游预期
- 控制流节点分支判断出错

## 4. 对话与事件流

对话流和检索流有关，但它更关注“连接、状态、流式输出、历史保存”。

```mermaid
sequenceDiagram
    participant FE as Frontend
    participant API as dialog_app
    participant SVC as dialog service
    participant ENG as rag / agent
    participant LLM as model service
    participant DB as storage

    FE->>API: 发起聊天请求
    API->>SVC: 解析会话与参数
    SVC->>DB: 读取历史上下文
    SVC->>ENG: 执行 RAG 或 Agent
    ENG->>LLM: 调用模型
    LLM-->>ENG: 流式返回 token / 结果
    ENG-->>API: 输出事件流
    API-->>FE: SSE / WebSocket 推送
    SVC->>DB: 保存消息与状态
```

关键目录：

- [api/db/services/dialog_service.py](../../api/db/services/dialog_service.py)
- [api/db/services/dialog_service.py](../../api/db/services/dialog_service.py)
- [rag/llm/chat_model.py](../../rag/llm/chat_model.py)
- [web/src/](../../web/src/)

## 从排障角度怎么使用这篇文档

如果你在排查问题，可以先判断问题属于哪一条流：

| 现象 | 优先查看 |
|------|------|
| 文件上传成功但没有可检索内容 | 文档处理流 |
| 检索结果很差或答非所问 | 检索生成流 |
| 工作流节点没有按预期执行 | Agent 执行流 |
| 前端收不到流式结果或历史错乱 | 对话与事件流 |

## 调试顺序建议

推荐的排查顺序：

1. 先确认入口层是否收到请求
2. 再确认服务层是否完成编排
3. 再确认核心引擎是否真正执行
4. 最后确认外部依赖是否返回预期结果

这样比一开始就深挖底层实现更高效。
